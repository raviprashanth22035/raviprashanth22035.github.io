Brand-ready forms on Edge Delivery Services

5 Nov 2026 | 4 min read

I wanted to see how far Edge Delivery Services could go for forms without a heavy AEM backend. So I built a proof of concept on Adobe's forms boilerplate, authored in da.live, and pushed on three things: how forms are authored, how they get branded, and where AI can help without getting in the way.

Forms as sheets

Each form is a da.live sheet. One row is one field, with columns for name, label, type, mandatory, placeholder, options, error message, a rule expression and a style hint like col-6 for half-width fields. The form block turns the sheet into a working form. A signup form with names, an email, a team dropdown and a country list needed no code at all.

Branding without CSS per brand

Every new brand or event wants its own logo, colours and font. I did not want a stylesheet for each one, so I used the bulk metadata that EDS already has.

  • One metadata sheet at the site root, with a URL column that takes glob patterns such as /brand/**.
  • One column per property: title, subtitle, description, logo, background, text and link colours, card colour and font.
  • A small function in scripts.js reads those values and sets CSS custom properties on :root. A banner is added only when a logo is present, so internal test pages are untouched.

Adding a brand is now two authoring steps: add a row to the sheet, then author pages under that prefix. A page's own metadata still wins, because that is how the platform behaves.

Two things bit me. The title property ends up in the page's title element, so any rich text typed into it is flattened to plain text. A separate subtitle property fixed that. And EDS auto-wraps classed divs placed as section children, then mistakes the wrapper for a block, so the logos are added as bare picture elements.

Submitting without a backend

I did not have AEM cloud access during the build, so submissions went to a Google Apps Script web app. That endpoint cannot answer a CORS preflight, and a JSON content type or any custom header triggers one. The fix is to keep the request a browser simple request:

headers = { 'Content-Type': 'text/plain;charset=utf-8' };

I added unit tests for the submit button too, including the case where a sheet sets both a redirect URL and a thank-you message. The redirect wins.

AI at the edge, kept on a short leash

The AI part is a local prototype: a Cloudflare Worker that sits in front of the dev server and calls a local model. It does two things.

  • Translation. When a form's JSON is requested with a language parameter, the worker translates only the display text: labels, descriptions, placeholders, error messages and option names.
  • A team popup. It fetches a real next-game date from a public sports API and has the model write one line around that fact.

The model never sees option codes, field names or rule expressions. The rule engine and the submitted payload depend on those exact values, so they stay out of the prompt.

If the model is down or returns bad JSON, the worker serves the original form. Translations are cached against the exact source JSON, so editing the sheet triggers one fresh translation and nothing more. It is a prototype, not a production setup. Dropdowns with more than 60 options are skipped, and the language is an explicit choice from the visitor, not geo detection.

What I would carry forward

  • Keep AI away from anything the logic depends on. Let it touch words, not values.
  • Make failure invisible. A form that falls back to English beats a broken one.
  • Push variation into authoring. A sheet row is cheaper than a code change.
  • A text/plain request is the quickest way past a CORS preflight.
